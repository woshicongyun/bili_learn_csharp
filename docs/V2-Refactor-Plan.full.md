# V2 重构方案（方案B：Capabilities 分层）

> 决策日期：2026-08-23
> 背景：V1 队列改造完成后，确立 V2 以「纵切式架构 + 渐进迁移」为方向。
> 选型依据：从 Token 维护成本出发，方案B（分层）最小化「读无关代码」，是 AI 维护者最省 token 的架构。

## 一、架构目标（纵切式，告别横向三层）

痛点：V1 改一个功能要跨 入口层→编排层→服务层→处理器层 四处跳，认知负担大，AI 维护极易改坏、反复试错烧 token。

V2 按业务能力竖切，每条竖柱自成闭环：

```
BiliLearn/
├── Entry/                    # 入口层（唯一暴露 XML 函数的地方）
│   ├── BiliLearnModule.cs    # 路由 + 配置声明 + Poke 转发（永远瘦，只做路由）
│   └── Bootstrapper.cs       # 服务装配（DI 容器）
│
├── Capabilities/             # ← 纵切核心：一个能力一条柱
│   ├── Learn/
│   │   ├── ILearnService.cs
│   │   ├── LearnService.cs       # 单视频学习流程
│   │   ├── LearnQueue.cs         # 队列调度（预下载并行+分析串行）
│   │   └── LearnModels.cs        # 该能力专属状态/结果模型
│   ├── Search/
│   │   ├── ISearchService.cs
│   │   ├── SearchService.cs      # WBI 签名搜索
│   │   └── SearchModels.cs
│   ├── Auth/
│   │   ├── IAuthService.cs
│   │   ├── AuthService.cs        # 扫码登录/登出/Cookie 持久化
│   │   └── AuthModels.cs
│   ├── Analyze/                   # 共用分析管线（视觉/ASR/字幕）
│   │   ├── IAnalyzer.cs
│   │   ├── VisionAnalyzer.cs
│   │   ├── AudioAnalyzer.cs
│   │   ├── SubtitleAnalyzer.cs
│   │   └── AnalyzeModels.cs
│   └── Quote/                     # 资讯/总结
│       ├── IQuoteService.cs
│       ├── QuoteService.cs       # conclusion 接口
│       └── QuoteModels.cs
│
├── Shared/                    # 跨能力共享（稳定、不常改）
│   ├── BilibiliApiClient.cs  # HTTP + WBI 签名 + Cookie 注入
│   ├── LLMClient.cs          # OpenAI 兼容封装
│   ├── FFmpegHelper.cs
│   └── Models/               # 基础领域模型（VideoInfo 等）
│
├── Storage/                   # 知识库/归档（独立，后续可接 SQLite）
└── Docs/                      # 每个能力一本自述文档
```

**核心规则**：
1. 改一个能力只动柱子里自己的文件，别的不碰
2. 每条柱自带完整三件套：接口 + 实现 + 模型 + 自述文档
3. 新增能力 = 新增一条柱，不动现有柱
4. 入口层永远瘦：Module 只做路由，不碰业务

## 二、迁移策略（渐进式，不推倒重来）

原则：`V1 能用就先跑着，新能力在哪、V2 就拆到哪`。

- **阶段一（本次）**：搭 V2 骨架（Entry + Bootstrapper + Capabilities 空目录 + Shared 基建）
- **阶段二**：把 Learn 柱完整落地（含队列），切 V2 入口生效，V1 并行保留可回滚
- **阶段三**：逐柱迁移 Search / Auth / Analyze / Quote
- **阶段四**：V1 废弃，V2 单飞，整理 Storage（接 SQLite）
- 每个阶段独立编译 + 实测通过才进下一阶段

## 三、技术要点

1. **队列状态机**：`VideoStatus` 升级为带转移校验的状态机，非法转移（如 `Analyzing→Queued`）直接拒绝
2. **并发控制集中化**：下载并发（默认2）和分析串行的信号量统一放进 `LearnQueue`，不散落各处理器
3. **接口优先**：每条柱先定接口再写实现，方便以后换 LLM 供应商/字幕源/存储
4. **SQLite 二期落地**：等队列稳定后再把 Storage 落库

## 四、选型备忘（为什么选方案B而不是A/C）

| 方案 | 找文件 | 改动面 | 长期 token 成本 |
|------|--------|--------|----------------|
| A 扁平 | 快但入口变胖 | 每次读全量入口 | 半年后膨胀，隐性黑洞 |
| B 分层 | 一次定位 | 锁死在柱内 | **最少，省在"不读无关代码"** |
| C 折中 | 快但无边界 | AI 易误读相邻文件 | 反复试错，最不可控 |

**结论**：4750 万 token 的大头耗在「读无关代码」，方案B 最小化这一点，虽建目录多花点，但每次维护省在刀刃上，30 次/月修改下三个月回本。

## 五、执行注意事项

1. 代码文件一律走 Python+REST API，不用 write 覆盖（避免转义损坏）
2. 部署区（`C:\Users\SEELE\Documents\Alife\Storage\Plugins\Alife.Plugin.BiliLearn`）是唯一真源，Git 是备份
3. 修改前先备份，改完必须编译验证 + 实测
4. 每个阶段独立编译 + 实测通过才进下一阶段

## 六、四阶段 Token 占比与外包分工

> 决策依据：2026-08-23 单日消耗 4750 万 token，大头耗在「读无关代码」。外包策略核心：把搬移类低风险活甩出去，自己专注框架耦合与正确性。

### Token 占比

| 阶段 | 内容 | Token 占比 | 风险 |
|------|------|-----------|------|
| 一 | 搭 V2 骨架（Entry + Bootstrapper + Shared） | 8%~12% | 高（框架耦合） |
| 二 | 拆 Learn 柱（队列状态机 + 并发） | 30%~35% | 高（状态机正确性） |
| 三 | 拆 Search / Auth / Analyze / Quote | 35%~40% | 低（纯搬移） |
| 四 | 废弃 V1 + Storage 落库（SQLite） | 15%~20% | 中（SQLite 新增） |

### 外包分工

| 阶段 | 外包与否 | 分工 |
|------|---------|------|
| 一 | ❌ 不外包 | 真央亲自搭。框架耦合深（PluginLoadContext/XmlHandlerTable），弱模型易翻车 |
| 二 | ⚠️ 半外包 | 真央写 Learn 柱规格书（状态机转移表+并发模型+接口签名），弱模型照填实现；测试用例真央亲自写，验收严格 |
| 三 | ✅ 全外包 | 纯搬移，给清「从哪搬到哪、接口长啥样」，弱模型能胜任，token 省最多 |
| 四 | ⚠️ 半外包 | 真央出 SQLite ER 图，弱模型照图建表；废弃 V1 真央亲自盯，防误删 |

### 外包优先级

🥇 最推荐：阶段三（纯搬移，规格清楚，省最多）
🥈 次推荐：阶段二（需给足规格，测试亲自盯）
🥉 半外包：阶段四（给 ER 图，盯废弃）
❌ 不外包：阶段一（框架耦合深）

### 核心原则
1. 把最费 token 的搬移类活甩给弱模型
2. 真央专注框架耦合（Bootstrapper）与正确性（状态机）
3. 每个阶段独立编译 + 实测通过才进下一阶段

## 七、瘦身预估

### 代码量变化

| 维度 | V1 现状 | V2 拆分后 | 变化 |
|------|--------|----------|------|
| 总行数 | 约1400（11文件） | 约1000~1100 | **-20%~25%** |
| 文件数 | 11 | 15~18 | +（每个更小） |
| BiliLearnModule.cs | 294行 六职共存 | 40~60行 纯路由 | **-80%** |
| 重复代码 | 多处搬运+残留 | 收进 Shared | 明显减少 |

### 变瘦的原因
1. 去掉 V1 反复重构留下的死代码、注释块、搬移残留
2. Shared 收拢共用（BilibiliApiClient 从三处重复变一处）
3. 接口替代实现依赖，接线代码变薄

### 不会"瘦一半"的原因
1. 状态机（VideoStatus 升级带转移校验）是新增逻辑
2. 队列并发是重构不是删除
3. SQLite（阶段四）是纯新增

### 核心结论
**代码瘦 20%~25%，瘦在"去重+清残留+入口变薄"**。但真正的价值是**认知瘦身**：文件数虽变多，每次改动读的文件变少了，这才是省 token、省脑力的关键。

## 八、扩展能力规划（评论区 + 视频标签）

> 背景：为知识库重构打基础。现状——评论区完全未接入，视频标签无专项抽取逻辑（接口有返回但未归档）。

### 扩展一：评论区抽取（新数据源）

- **落地位置**：新增 `Capabilities/Comments/` 柱
- **接口**：`/x/v2/reply/main`（按 cursor 翻页，拉热评 + 时间线）
- **处理**：LLM 提炼「用户观点 / 补充信息 / 争议点」，作为视频元数据进知识库
- **价值**：评论区是「用户视角的二次理解」，热评常补充视频没讲的坑
- **token 估算**：约 8%~10%（接口翻页 + LLM 提炼观点，新逻辑偏重但独立）

### 扩展二：视频标签抽取

- **落地位置**：`Shared/Models` 补 `Tags` 字段，`Learn` 柱归档时抽取
- **处理**：视频详情接口取 `tag` 数组归档；可选 LLM 归一（"AI""人工智能"→"AI"）
- **价值**：为知识库**分类检索**打基础——按标签找视频，不用全量扫
- **token 估算**：约 3%~5%（接口已有数据，解析 + 归档 + 可选归一，轻量）

### 对知识库重构的价值

补齐知识库的**元数据维度**：
- 正文语义 = 「视频讲了什么」（现有）
- 分类索引 = 「视频属于什么」（标签）
- 群体反馈 = 「观众怎么看」（评论区）

三者合一，知识库从「内容库」升级成「立体语义库」，SQLite 落库时一起设计。

### 外包建议

| 扩展 | 外包可行 | 分工 |
|------|---------|------|
| 评论区 | ⚠️ 半外包 | 真央出接口规格 + 提炼 prompt，弱模型实现翻页逻辑；观点提炼质量真央把关 |
| 标签 | ✅ 适合外包 | 逻辑简单（解析 + 归档 + 归一），给清字段定义即可 |

### 对四阶段的影响

- 阶段三（拆柱）时顺带把评论区和标签并进对应柱子，不额外增阶段
- SQLite 落库（阶段四）的 ER 图需含 `tags` 与 `comments` 表
